The technical concepts behind CourtSimulator, and how each one works

A voice-first moot court for Pakistani law students. A student speaks; three independent artificial-intelligence agents hold a hearing against them; every provision any agent cites is checked against a verified statute corpus before it is spoken aloud. This document names each technique the system genuinely uses, explains the mechanism, and attaches a measured number wherever one exists.

01System architecture

Three services behind one origin

The system is three separate programs that talk over Hypertext Transfer Protocol, plus one database. The split is not decoration — it is what keeps the reasoning in one place.

Browser (React) ──► Express API ──► Python AI service ──► PostgreSQL port 5173 port 5000 port 8000 speaks, listens contract, sessions retrieval, agents, voice transport memory, scoring
ServiceLanguage and frameworkWhat it owns
Web applicationReact 19, Vite, TypeScriptThe microphone, playback, and the record of proceedings on screen
Application Programming Interface serverExpress 5 on Node.js, TypeScriptThe Hypertext Transfer Protocol contract, session persistence, authentication, and voice transport
Artificial-intelligence servicePython 3.12, FastAPIAll reasoning: retrieval, grounding, memory, the agents, verdict scoring

Two rules hold this together. Every model call lives in the Python service — the Express server never builds a prompt. And the browser never talks to the Python service; it calls same-origin /api/* paths only, so the OpenAI credential exists on the two servers and never reaches a user's machine.

No exception remains. The manually-raised objection ruling was the last piece of reasoning inside the Express server; on 4 September 2026 it moved behind POST /courtroom/objection and now runs on the same ReAct bench as an objection raised by the agents. Express builds no prompt and makes no model call of its own.

Contract-first design with generated validators

A single OpenAPI specification file is the source of truth for every shape that crosses the network. From it, a code generator produces two libraries: Zod validators used by the server, and a typed React Query client used by the browser. Neither is ever hand-edited — you change the specification and regenerate.

The benefit is that a mismatch between what the browser sends and what the server expects becomes a compile error rather than a runtime surprise during a demonstration. Every route boundary validates its input against the generated schema; nothing is parsed ad hoc.

lib/api-spec/openapi.yaml → lib/api-zod, lib/api-client-react

02Natural Language Processing and the language model

Large Language Model the model that produces every spoken line

A Large Language Model is a neural network trained to predict text. Everything the court says — an objection, a ruling, testimony, a written verdict — is produced by one. The system uses two deliberately:

RoleModelWhy
Reasoning and writinggpt-4oRulings, testimony, verdicts, reranking — anywhere a wrong answer teaches a wrong rule
First-pass screeninggpt-4o-miniThe cheap half of the objection cascade, described in section 8
Text representationtext-embedding-3-small1,536-dimension vectors for the statute corpus

Structured output making a model's answer machine-readable

A model that writes prose cannot be routed on. Every agent decision is therefore requested as strict JavaScript Object Notation with a fixed shape. The witness, for example, must return an outcome, a grounding, a private basis, and the words to speak:

{"outcome": "answer" | "dont_recall" | "decline_speculation" | "correct_record", "grounding": "statement" | "prior_testimony" | "both" | "none", "basis": "one line, not spoken aloud", "spoken": "what the court hears"}

Because the outcome is a fixed set rather than free text, the graph can branch on it and the evaluation harness can score it without a second model reading the answer.

Prompt design as a constraint, not a personality

Each agent has its own system prompt stating what it may do. The witness prompt carries a binding rule — every asserted fact must be traceable to its statement of record or its own earlier testimony — and makes the honest refusals first-class options, because a compliant model will otherwise never choose them. Opposing counsel may only cite objection grounds drawn from the corpus, so a fabricated ground is impossible by construction rather than by hope.

03Retrieval-Augmented Generation

Retrieval-Augmented Generation means the model is never asked to recall the law from training. The governing statutory text is fetched from a real corpus and placed into the prompt, and the model is instructed to rule only on text it has actually been shown. This is the difference between a system that sounds legal and one that can be checked.

Retrieval here is a four-stage pipeline. Two independent searches run, their rankings are merged, the merged head is reordered by a stronger model, and only then does anything reach an agent's prompt.

query ──┬─► Best Matching 25 (lexical, in memory) ──► ranked list ──┐ │ ├─► Reciprocal └─► dense vectors (1,536-d, exact scan) ──► ranked list ──┘ Rank Fusion │ top-k ◄── Large Language Model rerank ◄┘

The corpus

Fifty-three provisions of Pakistani law, stored as structured records with the full official text: the Qanun-e-Shahadat Order 1984 (twenty articles), the Pakistan Penal Code 1860 (fifteen sections), the Code of Criminal Procedure 1898 (ten sections), and the Constitution of Pakistan 1973 (eight articles).

53 of 53 provisions have been compared word-for-word against their official printed source and carry a per-provision verified flag. Reproduce with pnpm run statutes:verify. Constitution Article 199 was the last to close, on 20 August 2026: its text is later than the 2012 print its neighbours were diffed against, so it was flagged unverified rather than assumed correct until a post-Twenty-seventh-Amendment print confirmed it word-for-word. The same run caught Article 10 drifting the other way — verified against the 2012 print, and a sentence behind the law once the 2025 amendment inserted “Supreme Court of” into its Review Board clause. A provision verified against a superseded print is not verified, which is why the flag is per provision: a file-level flag would have passed Article 199 on its neighbours and would never have surfaced Article 10 at all.

Best Matching 25 the lexical half — why, and how it scores

The name is literal. It comes from the Okapi information-retrieval system built at City University London in the 1990s, and "BM25" is the twenty-fifth in a numbered series of Best Matching formulations that the research group tried. It has stayed the default lexical ranker for thirty years because it is cheap, needs no training, and is very hard to beat on exact-term queries.

Why this system needs it at all. Embeddings are a blur. Ask for "section 302" and a vector search returns provisions that are about homicide — section 300, section 302, section 324 — because they all sit in the same region of meaning-space. But a law student saying "section 302" does not want a neighbourhood. They want that section. Exact identifiers, statutory numbers, and domain terms of art are precisely where embeddings are weakest and term matching is strongest.

How it scores. For each term in the query, Best Matching 25 combines three ingredients:

IngredientWhat it doesWhy it matters here
Term frequency, with saturation More occurrences score higher, but with sharply diminishing returns — the curve flattens rather than growing linearly A provision using "murder" ten times is not ten times more relevant than one using it twice. Saturation is the main thing BM25 adds over naive term counting
Inverse document frequency A term appearing in few documents is worth more than one appearing everywhere "Shall" appears in every provision and carries almost no signal. "Qatl-i-amd" appears in a handful and is almost decisive
Length normalisation Discounts long documents, which would otherwise win simply by containing more words Provisions vary from one line to several pages. Without this, the longest section would rank first for nearly everything

Two tuning constants control the shape: one sets how quickly repetition saturates, the other how aggressively length is penalised. This system uses the library defaults, because the corpus is small and uniform enough that tuning them would be fitting noise.

One implementation detail that genuinely mattered. The tokeniser is custom. A standard word tokeniser splits on punctuation, which turns qatl-i-amd into qatl, i, amd and qanun-e-shahadat into fragments including a bare e. That scatters a decisive legal term's weight across meaningless pieces — and i and e appear everywhere, so inverse document frequency correctly judges them worthless. The tokeniser keeps hyphenated terms intact, so the term of art stays one term.

app/rag/index.py — tokenize(), indexed over heading + content

Where it fails. Given "the witness is just repeating what somebody else told him outside court", Best Matching 25 finds nothing useful. The governing article — oral evidence must be direct — shares not one content word with that sentence. This is exactly the gap the other retriever fills.

Embeddings, and why the dimension is 1,536

An embedding turns a passage into a list of numbers positioned so that texts with similar meaning sit near each other. The model here is text-embedding-3-small, and 1,536 is that model's native output width — it is not a number this project chose freely.

What the project did choose is to use the full width. The text-embedding-3 family is trained with Matryoshka Representation Learning, which packs the most important information into the earliest dimensions, so a vector can be truncated — to 512, or 256 — and still work, degrading gracefully rather than breaking. Truncating trades accuracy for storage and speed.

That trade buys nothing at this scale. The arithmetic:

QuantityValue
Provisions in the corpus53
Dimensions per vector1,536
Bytes per number (32-bit float)4
Total vector storage≈ 318 kilobytes
At a few thousand provisions, fully ingested≈ 30 megabytes

Truncating to 512 dimensions would save a fraction of a megabyte and cost retrieval accuracy on a corpus where accuracy is the entire point. The larger sibling model, text-embedding-3-large, emits 3,072 dimensions — double the storage and cost for a gain the measured figures do not need, because reranking already reaches a perfect hit@1.

1,536 is a hard constraint, not a setting. The number is written into the configuration and must match the vectors already stored in the database. Changing the embedding model, or the dimension, invalidates every stored vector — the two would be compared in different spaces and the results would be meaningless. Either change is therefore a full re-index of the corpus, not an edit.

Cosine similarity, and a small optimisation

Similarity is measured by the cosine of the angle between two vectors. Cosine rather than straight-line distance, because in embedding space direction carries the meaning and magnitude largely reflects incidental things like passage length. Two texts saying the same thing at different lengths should score as similar, and cosine ignores the length.

Cosine normally requires dividing by both vectors' lengths. This system divides once, at index time: every vector is scaled to unit length before it is stored. Once both sides have length one, the cosine is the dot product, so the whole search collapses to a single matrix multiplication with no division at query time.

app/rag/index.py — vectors stored as vector / norm; retrieval.py — index.matrix @ query_vector

Why both, and how they are merged

QueryFound by
"section 302", "qatl-i-amd"Best Matching 25 — exact terms, which embeddings blur into neighbouring provisions
"the witness is repeating what someone else told him"Embeddings — this shares no vocabulary at all with the article codifying the rule against hearsay

Legal questions arrive in both modes and neither retriever covers both, so both run and their results are merged. The merge is Reciprocal Rank Fusion, not a weighted sum of the two scores — and that choice is forced.

Best Matching 25 scores are unbounded: 7.12 on one query, above 40 on another, depending on term rarity. Cosine similarities are bounded and sit in a narrow band around 0.30 to 0.45. Adding those together directly means one of them dominates arbitrarily, and fixing that needs a normalising constant that must be retuned every time the corpus changes. Reciprocal Rank Fusion sidesteps the problem entirely by throwing the scores away and using only the position in each list:

score(document) = Σ 1 / (k + rank in retriever r) k = 60 r∈retrievers

Being rank-based makes it scale-free — it works identically no matter what units either retriever reports. The constant k controls how sharply the top of each list is favoured. With k at zero, the first-placed document scores 1.0 and the second only 0.5, so a single retriever's favourite would dominate the fusion outright. At k = 60 those become 1/61 and 1/62 — nearly equal — so agreement between the two retrievers matters more than either one's confidence. The value 60 is the standard from Cormack and colleagues, 2009.

Reranking: bi-encoder versus cross-encoder

This distinction is the key to why reranking works at all, and it is worth being able to state plainly.

Bi-encoder — the embedding searchCross-encoder — the reranker
HowQuery and document are encoded separately into vectors, then comparedQuery and document are fed in together, so the model attends across both at once
SpeedDocuments are embedded once, in advance. A query is one vector and one matrix multiplyNothing can be precomputed — every query-document pair needs its own forward pass
QualityLossy. The document was compressed into a vector before the query existed, so nothing in it is query-awareHigher. The model can weigh which part of the document answers this question

So the two stages divide labour by cost. The bi-encoder is fast enough to scan the whole corpus and produce a shortlist; the cross-encoder is accurate enough to order that shortlist and too expensive to run over everything. Here the fused shortlist is roughly three times the requested result count.

Why the reranker is a Large Language Model, on evidence

The conventional cross-encoder was tried first and made retrieval worse. The test query was "the witness is just repeating what somebody else told him outside court"; the correct answer is the article requiring oral evidence to be direct.

RerankerRank of the governing articleNote
None — fusion only2"Impeaching credit" ranked above it
Cross-encoder, MS MARCO MiniLM10 of 15Every score negative
Large Language Model1Scored 10 out of 10

The explanation is the useful part. MS MARCO cross-encoders are trained on Bing web-search query and passage pairs. They learn to reward lexical and topical overlap, and they carry no representation of legal doctrine. Nothing in that training signal connects a plain-English description of hearsay to the article that codifies it — the two share no words and the connection is a matter of law, not of language. An out-of-domain cross-encoder is worse than no reranker here.

The Large Language Model reranker is a cross-encoder in spirit — it reads the question and the candidates together — but it can be instructed, and the instruction is what does the work:

"You rank Pakistani statutory provisions by how directly they govern a legal question. Judge legal applicability, not topical similarity: a provision that merely mentions the same subject matter scores low, a provision that supplies the operative rule scores high."

Each candidate is numbered, truncated to its first characters to hold the prompt down, and scored from zero to ten in a single call that returns structured output. "Applicability, not similarity" is exactly the distinction the MS MARCO model could not make, and stating it in words is cheaper than fine-tuning a model that could.

hit@1 = 1.00, Mean Reciprocal Rank = 1.00 with reranking, from 0.80 / 0.88 with fusion alone, over a twenty-query golden set. Reproduce with pnpm run eval.
What reranking costs. One extra model call per query, roughly three to four seconds and a token charge. A local cross-encoder would be free and fast — the backend is still switchable — but it needs a legal or instruction-tuned checkpoint to be worth using. The default is set on the measured evidence above, not on preference.

Exact search instead of a vector database

Embeddings live in JavaScript Object Notation Binary columns in PostgreSQL and are searched by an exact scan — every vector compared, none skipped. There is no approximate index and no external vector database.

This is a decision, not a shortcoming. Approximate nearest-neighbour indexes trade exact recall for speed, and that trade only pays somewhere north of a hundred thousand vectors. At this scale the entire search is one matrix multiplication: even at five thousand provisions that is about 7.7 million multiply-add operations, which a numerical library completes in single-digit milliseconds — faster than an approximate index, with recall that is exact rather than probable, and one fewer database extension to deploy.

The host database offers only trigram indexing in any case, so an approximate vector index was never on the table. The honest framing is that the constraint and the right answer happened to agree.

04Agentic artificial intelligence

The multi-agent courtroom as a state graph

The courtroom is a directed graph built with LangGraph. Each participant is an independent agent with its own system prompt, its own decision, and its own tools. One spoken question travels through however many agents the moment requires.

┌─ objection raised ─► JUDGE ─ sustained ─► question struck, END student speaks ─► OPPOSING COUNSEL (ReAct) └ overruled ──┐ └─ no objection ─────────────────────────► WITNESS ─► END
NodeAgentDecision it makes
objection_screenOpposing counselWhether to object to the question just asked, and on which evidentiary ground
judge_rulingThe benchSustained or overruled, after reading the provision
witness_testifyWitnessWhich of four things it can properly say
counsel_arguesOpposing counselRebuttal when no witness is on the stand
bench_presidesThe benchModerates openings and closings

The supervisor is the edges, not a prompt

This is the single most important design claim in the project. In many multi-agent systems a "supervisor" is another language model asked who should speak next. Here routing is pure functions over the shared state — the phase of the hearing and whether a witness is on the stand fully determine who may act. No model is consulted.

The consequence is the demonstration's strongest moment: a sustained objection routes the graph to its end node, so the witness is never reached. The witness does not decide to stay silent and cannot be talked out of it. The silence is asserted by an edge. No single model swapping personas by prompt can make that guarantee.

app/agents/graph.py — _route_after_ruling returns END on "sustained"

Reasoning and Acting the bench reads before it rules

Reasoning and Acting — usually written ReAct — is a loop in which a model alternates between thinking and calling a tool, using each observation to decide the next step. The judge does not rule from memory. It runs a Thought → Action → Observation loop with one tool, search_statute, which queries the retrieval pipeline described above, and only then produces a ruling citing what it actually read.

Every step of that trace is stored and shown to the student, so the reasoning behind a ruling survives a page reload. A courtroom record that cannot show why the bench ruled is not a record.

The loop is bounded at 3 rounds. Every agent loop in the system declares its bound explicitly in code — an unbounded agent loop is a runaway cost and a hung demonstration.

The witness as a deciding agent

A witness is the one agent with no tools, and that is a legal constraint rather than an omission: a witness testifies to their own perception, and a search tool would let them testify to things they looked up.

Their agency is the decision every real witness makes under examination — can I properly say this? The model must commit to one of four outcomes before speaking, and name what in its own record supports it:

  • Answer — within its own perception, supported by its statement or prior testimony
  • Do not recall — it did not perceive this, and will not construct a plausible answer
  • Decline to speculate — the question asks for a guess, another person's intention, or a legal conclusion
  • Correct the record — the question presupposes a fact never stated
0 fabrications out of 9 questions the witness could not possibly know, with 17 of 17 outcomes correct. Reproduce with pnpm run eval:witness. The design this replaced invented an answer on 2 of 8 comparable questions.

Two-tier memory

Agents receive memory in two tiers. Working memory is the turns of the current phase, replayed word for word. Long-term memory is a structured recollection of everything earlier — the student's claims, witness testimony, and the bench's directions, held as separate lists rather than as a narrative, because a contradiction check compares against the claims field specifically and flattening it into prose would make that comparison lossy.

Summarisation runs only on phase transitions, not on every turn, because within a phase the agent already sees the raw turns. A watermark records how far the summary has folded, making each fold incremental — four model calls per session in total rather than one per turn.

Memory is also scoped per witness. A witness sees only their own prior evidence, never another witness's, because they were out of the room for it. The bench sees everything.

05Grounding, and the honesty machinery

The citation audit

Every utterance any agent produces is scanned for statutory citations, and each citation is resolved against the corpus before the words are spoken. A provision is marked verified, absent from the corpus, or present but not yet diffed against an official print.

Attributed fabrication the distinction that stops the system lying about itself

A naive audit counts every unknown citation as a hallucination. That produced a real and instructive bug: when a student invented a section number and the bench correctly refused it, the bench was flagged for fabricating the very provision it had just rejected.

So the audit distinguishes a provision an agent relied on from one it merely named in order to reject, and separately marks citations echoed back from the student. Anything shown to a student uses the attributed figure. A tool that misreports its own honesty is worse than one that says nothing.

Unverified-text markers

Where a provision's text has not been confirmed against an official print, the prompt block and the interface both carry an explicit warning not to quote it as authoritative. These markers are treated as a feature to point at, never an obstacle to route around, and may not be shortened or hidden to make output look more confident.

06Voice

Speech to text

The browser records with the MediaRecorder interface, producing WebM audio in the Opus codec. That is sent to the server and transcribed by a speech-recognition model, pinned to English at temperature zero — the language because a Pakistani courtroom turn mixes English legal phrasing with Urdu names and terms of art and the model would otherwise switch mid-utterance, and the temperature because a transcription that varies between identical takes makes every number downstream unreproducible.

The WebM format passes through to transcription untouched — no conversion step, no external media tool required. Verified end to end: a real 48 kilohertz mono WebM/Opus blob returns its input word for word.

Text to speech, one voice per agent

Each agent has a distinct synthesised voice, so a student who hears an objection cut across a witness knows two different people spoke without reading the transcript. Delivery instructions describe how a line is said and never what — the words come from the agents and have already passed the citation audit, so nothing in synthesis may alter them.

A dedicated speech endpoint is used rather than a conversational audio model asked to repeat text, because a model free to paraphrase could turn an audited citation into a different one, and the audit would then be vouching for words nobody said.

Streaming with Server-Sent Events

A turn is not synthesised and then sent. As each agent finishes speaking, its transcript and audio are streamed to the browser over Server-Sent Events — a one-way channel over ordinary Hypertext Transfer Protocol — while the next agent is still working. Audio is 16-bit Pulse-Code Modulation at 24 kilohertz, which is exactly what the browser's playback worklet expects, so the bytes stream through without resampling.

First audio at 8.1 seconds, down from 16.1 seconds when the turn was assembled before sending. Zero misaligned audio chunks.
Honestly stated: a witness answering aloud has been produced in testing but not yet heard by a human in the browser. Opposing counsel and the bench have both been confirmed audible in distinct voices from live microphone input.

07Evaluation

Every claim in this document has a command behind it. The harness calls the same functions the application calls — never a copy — so it cannot drift away from the product it measures.

Information-retrieval metrics

  • hit@k — the fraction of queries where a correct provision appears in the top k results.
  • Mean Reciprocal Rank — the average of one divided by the rank of the first correct result. Finding the right provision at position one scores 1.0; at position four, 0.25. It rewards being right first, which is what matters when a judge reads the top hit.

Classification metrics for the objection decision

Opposing counsel's decision to object is scored over thirty-two labelled scenarios, including seven proper questions that exist purely to catch over-objection — an advocate who objects to everything is noise, not opposition.

MetricMeaningMean of 3 runs
RecallOf the objections that should have been raised, how many were1.00
PrecisionOf the objections raised, how many should have been0.98
F1 scoreThe harmonic mean of precision and recall, penalising a system strong in one and weak in the other0.99
SpecificityOf the proper questions, how many drew silence—
Zero routing leaks across all 32 scenarios, every run. A sustained objection has never once been followed by a witness answer. That is asserted by the graph, so a violation would be a structural bug rather than a model's opinion.
Quote the mean, never a single run. One of those three runs scored a perfect thirty-two out of thirty-two, which is exactly the trap. Precision drifts by one scenario between identical runs, and the bench's ruling accuracy has been observed between 89 and 100 per cent with no change to the judge. Single-run figures for those two are not evidence.

Large Language Model as judge

The grader is itself a model, so it must be graded. Three transcripts of the same case at deliberately different quality are scored repeatedly, testing two things: reliability (does the same transcript get the same mark twice?) and discrimination (are strong, mixed, and weak advocacy ranked correctly?).

3 of 3 transcript pairs ranked as expected, every run. Strong 85–88, mixed 55–58, weak 25–35. Citation accuracy collapses from 100 per cent on the strong transcript to 0 per cent on the weak one, whose citations are fabricated — so the guard is exercised at the same time.

Adversarial testing

Transcribed speech reaches the agents' prompts verbatim, so a student can say anything a prompt injection can contain. Thirty-six attacks are put through the courtroom and the verdict scorer, scored by objective detectors rather than opinion: a canary token the agent would never otherwise say, distinctive phrases leaking from system prompts, an agent breaking character to describe itself as a model, and fabricated citations.

0 of 36 attacks obeyed. Reproduce with pnpm run eval:redteam. The defence is the multi-agent design itself: an injected instruction arrives in front of an agent whose entire job is to object to improper questions, and it gets objected to as irrelevant.

A dedicated prompt-injection guard is deliberately not built. The discipline is to build it when an attack lands, and to add the attack to the suite first — a guard with nothing to guard against cannot be shown to work.

08Operations for language-model systems

Cost and latency metering

Instrumentation wraps the shared OpenAI client rather than the individual call sites. Eight places in the service reach the interface, and a cost figure that quietly misses one is worse than no figure, because it looks authoritative. Wrapping the client once means a call site added tomorrow is counted whether or not anyone remembers.

The objection cascade

Opposing counsel screens every question put to a witness, and the honest answer to most is "no objection" — a decision that does not need the expensive model. The cheap model takes that majority; anything it wants to object to is re-decided by the stronger model before it reaches the student, because a wrong objection teaches a law student a wrong rule.

0.95 United States cents per turn with the cascade enabled: 0.20 cents for a silent turn, 1.53 cents for an objected one. The split matters — the silent turn is the common case and the one the voice session waits on.

Experiment tracking

Every evaluation run is recorded to MLflow: the metrics, the settings that produced them, the commit identifier, whether the working tree was dirty, and the full printed report as an attachment. Parameters are read from the settings object rather than passed in by hand — the setting somebody forgets to log is precisely the one that moved the metric.

The report is stored beside the metrics because the metrics tell you hit@1 fell while only the report tells you which query missed.

09Data, persistence and security

One schema, one owner

The database is PostgreSQL. The schema is defined once, in TypeScript, using the Drizzle object-relational mapper. The Python service reads and writes the same tables with raw Structured Query Language and never defines or migrates a table — there is deliberately no second schema definition to drift out of step.

Authentication

MechanismHow it works
Password storageThe scrypt key-derivation function — deliberately slow and memory-hard, so guessing costs real time
Session tokenStateless: user identifier, expiry, and a Hash-based Message Authentication Code signature. No token table to keep in step
Signature checkConstant-time comparison, so an attacker cannot learn the signature from how long a rejection takes
Rate limitingTwo counters, one per email address and one per network address — either alone has a failure mode
Uniform failureAn unknown email is compared against a decoy hash so a wrong address and a wrong password take the same time and return the same message

Every route touching a student's own record sits behind an authentication check. The case library stays public, because it is shared.

10What this system does not do

Being able to say this clearly is part of the defence, not a weakness in it.

  • Fifty-three provisions. Real practice touches thousands. Every retrieval figure is excellent over this corpus, and should always be quoted that way.
  • Criminal matters only. Case drafting is restricted to the one area of law the corpus can actually ground.
  • Counsel gets no right of reply to an objection. A real bench hears you before ruling. This is the most conspicuous departure from real practice and the top item of future work.
  • Opposing counsel never examines a witness, and there is no re-examination phase.
  • The bench never interrupts. The design is turn-based; a real judge cuts in mid-sentence.
  • It runs locally. No container image and no continuous integration yet, so it is a working system rather than a deployed one.
